# A10 — Разбор решения (спойлеры)

Примеры: `curl` на `http://127.0.0.1:8091` (vulnerable) и `http://127.0.0.1:8092` (fixed). В Windows удобнее Git Bash или WSL (или `curl.exe` в PowerShell).

## Дефект 1 — подробные ошибки в ответе

Нечисловой `month` приводит к необработанному исключению. «Отладочный» обработчик ошибок отдаёт клиенту всё:

```bash
curl -s "http://127.0.0.1:8091/report?month=abc"
# {"config": {"database": "sqlite:///:memory:", "env": "production",
#             "internal_api_key": "FLAG{a10_verbose_errors}"},
#  "error": "invalid literal for int() with base 10: 'abc'",
#  "trace": ["Traceback (most recent call last):",
#            "  File \"/usr/local/lib/python3.12/site-packages/flask/app.py\", line 917, in full_dispatch_request", ...]}
```

В ответе есть версия языка и фреймворка, пути к файлам и строки кода, а ещё внутренняя конфигурация с ключом. Для атакующего это готовая карта приложения.

**Правило:** клиенту: короткое нейтральное сообщение и `error_id`. Трассировка, конфигурация и детали остаются в логе сервера, а отладочные режимы в продакшене выключены.

**Fix:** единый обработчик возвращает `{"error": "внутренняя ошибка сервера", "error_id": "..."}`, а трассировка пишется в лог по этому `error_id` (`# FIX 1`). Ожидаемую ошибку ввода (`month` не число) приложение обрабатывает само и отвечает 400.

## Дефект 2 — fail-open в проверке доступа

Документ `3` «испорчен»: в `level` лежит текст `TOP`, а не число. Проверка доступа ловит любую ошибку и в этом случае разрешает доступ:

```bash
curl -s -c a.txt -X POST http://127.0.0.1:8091/login -H 'Content-Type: application/json' -d '{"username":"alice","password":"alice123"}'
for i in 1 2 3 4; do curl -s -b a.txt http://127.0.0.1:8091/documents/$i; echo; done
# 1: {"content": "Сегодня: борщ и плов.", ...}
# 2: {"error": "недостаточно прав"}
# 3: {"content": "FLAG{a10_fail_open} — бюджет на следующий год", ...}   <- должно быть закрыто!
# 4: {"error": "недостаточно прав"}
```

Здесь `int("TOP")` выбрасывает `ValueError`, а `except Exception: return True` превращает сбой в разрешение. В реальных системах такая ошибка возникает при испорченных данных, недоступном сервисе политик, таймауте или неожиданном вводе.

**Правило:** при сбое проверки доступа ответ по умолчанию «нет» (fail-closed). Ошибку при этом логируем, чтобы причину нашли и починили.

**Fix:** `except` возвращает `False` и пишет в лог, какая проверка не удалась (`# FIX 2`). Документ `3` в fixed закрыт для всех, пока данные не исправят.

## Дефект 3 — частично выполненная операция

Заказ из трёх кружек: на складе их две. Приложение сначала списывает деньги и только потом смотрит на склад:

```bash
curl -s -b a.txt http://127.0.0.1:8091/me
# {"balance": 100, ...}
curl -s -b a.txt -X POST http://127.0.0.1:8091/orders -H 'Content-Type: application/json' -d '{"item_id":1,"qty":3}'
# {"error": "на складе осталось 2, а нужно 3", "type": "RuntimeError", "trace": [...], "config": {...}}   (500)
curl -s -b a.txt http://127.0.0.1:8091/me
# {"balance": 40, ...}
curl -s http://127.0.0.1:8091/_lab/consistency
# {"flag": "FLAG{a10_partial_operation}", "money_lost": {"alice": 60}, "note": "деньги списаны, а заказов на эти суммы нет"}
```

60 списано, заказа нет. Каждый SQL-запрос сохранился сразу (автокоммит), а откатить «половину» операции нечем.

**Правило:** операция из нескольких шагов выполняется атомарно: всё или ничего. Это транзакция, а в распределённых системах компенсирующие действия (saga) и идемпотентность.

**Fix:** вся операция внутри `BEGIN IMMEDIATE` … `COMMIT`, при любой ошибке `ROLLBACK` (`# FIX 3`). Порядок шагов оставлен таким же, как во vulnerable, чтобы было видно: дело именно в транзакции. В fixed тот же заказ даёт 409, баланс остаётся 100, а `/_lab/consistency` показывает `{"money_lost": {}}`.

## Дефект 4 — нет лимитов

Нормальный запрос: картинка 800×600. Но верхней границы нет:

```bash
curl -s -X POST http://127.0.0.1:8091/thumbnail -H 'Content-Type: application/json' -d '{"width":800,"height":600}'
# {"estimated_mb": 1.83, "ok": true}
curl -s -X POST http://127.0.0.1:8091/thumbnail -H 'Content-Type: application/json' -d '{"width":20000,"height":20000}'
# {"error": "сервис упал: не хватило памяти"}   (500)
curl -s -b a.txt http://127.0.0.1:8091/me
# {"error": "сервис недоступен"}   (503)
curl -s http://127.0.0.1:8091/health
# {"flag": "FLAG{a10_no_limits}", "status": "crashed", ...}   (503)
curl -s -X POST http://127.0.0.1:8091/reset-lab
```

20000×20000 пикселей это почти 1,5 ГБ при 4 байтах на пиксель. Падение имитируется в лабе, но в жизни это OOM-killer, зависший процесс и недоступный сервис для всех. Отдельно нет ограничения размера самого запроса и таймаутов на долгую работу.

**Правило:** границы входных данных проверяем **до** того, как тратить ресурсы: размер тела запроса, размеры и количество элементов, глубина вложенности, время выполнения (таймауты), частота запросов (rate limit).

**Fix:** `MAX_CONTENT_LENGTH` (8 КБ, Flask отвечает 413 сам), допустимая сторона 1–2048 пикселей и проверка оценки памяти до обработки (`# FIX 4`). Тот же запрос получает 413, сервис продолжает работать.

## Дефект 5 — сырой текст исключения в ответе

Отчёта `q2` нет, а `archive` «битый» (на месте файла каталог). Приложение возвращает `str(e)`:

```bash
curl -s http://127.0.0.1:8091/reports/q1
# {"name": "q1", "text": "Отчёт за 1 квартал: выручка выросла на 4%.\n"}
curl -s http://127.0.0.1:8091/reports/q2
# {"error": "[Errno 2] No such file or directory: '/tmp/a10v_v0oz0vii/q2.txt'"}
curl -s http://127.0.0.1:8091/reports/archive
# {"error": "[Errno 21] Is a directory: '/tmp/a10v_v0oz0vii/archive.txt'"}
```

Из текстов ошибок видно операционную систему (путь `/tmp/...` или `C:\Users\<имя>\AppData\...` на Windows), каталог, где лежат данные, и логику приложения.

**Правило:** сообщение исключения предназначено разработчику, а не пользователю. Ожидаемые ситуации («нет файла») обрабатываем осмысленным ответом, неожиданные отдаём единому обработчику.

**Fix:** `FileNotFoundError` обрабатывается отдельно и даёт нейтральное «отчёт не найден» (`# FIX 5`), всё остальное попадает в единый обработчик и возвращается с `error_id`.

## Проверка fixed

```bash
curl -s "http://127.0.0.1:8092/report?month=abc"
# {"error": "month должен быть числом от 1 до 12"}   (400)
curl -s http://127.0.0.1:8092/reports/archive
# {"error": "внутренняя ошибка сервера", "error_id": "1d6406c3"}   (500; трассировка только в консоли сервера)
curl -s -c b.txt -X POST http://127.0.0.1:8092/login -H 'Content-Type: application/json' -d '{"username":"alice","password":"alice123"}'
curl -s -b b.txt http://127.0.0.1:8092/documents/3
# {"error": "недостаточно прав"}   (403)
curl -s -b b.txt -X POST http://127.0.0.1:8092/orders -H 'Content-Type: application/json' -d '{"item_id":1,"qty":3}'
# {"error": "недостаточно товара на складе"}   (409)
curl -s -b b.txt http://127.0.0.1:8092/me
# {"balance": 100, ...}
curl -s -X POST http://127.0.0.1:8092/thumbnail -H 'Content-Type: application/json' -d '{"width":20000,"height":20000}'
# {"error": "допустимая сторона: от 1 до 2048 пикселей"}   (413)
curl -s http://127.0.0.1:8092/reports/q2
# {"error": "отчёт не найден"}   (404)
```

Легитимные сценарии работают как раньше: `alice` читает документ `1`, `bob` читает документ `2`, обычный заказ одной кружки проходит, картинка 800×600 обрабатывается. Подробности каждой скрытой ошибки ищите в консоли сервера по `error_id`.

## Итог

| № | Дефект | Как показан | Что в fixed |
|---|--------|-------------|-------------|
| 1 | Подробные ошибки | Трассировка и конфиг с ключом в ответе на `?month=abc` | Единый обработчик: `error_id` клиенту, подробности в лог |
| 2 | Fail-open | Испорченный `level` открыл секретный документ | Fail-closed: сбой проверки означает отказ и запись в лог |
| 3 | Нет отката | 60 списано, заказа нет | Транзакция: при ошибке `ROLLBACK`, баланс не меняется |
| 4 | Нет лимитов | Один запрос 20000×20000 «роняет» сервис | Лимит тела запроса и размеров, 413 до выделения ресурсов |
| 5 | Сырой текст исключения | Путь к файлу на сервере в ответе | Нейтральные сообщения, детали только в логе |
