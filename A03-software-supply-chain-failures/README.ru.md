# A03 — Software Supply Chain Failures (сбои в цепочке поставок ПО)

**Статус:** ✅ готово

## О чём лаба

**Kestrel CI** — сайт вымышленного SaaS для сборки и доставки релизов: лендинг, тарифы, документация, страница сборок и реестр пакетов. Интерфейс на **английском, русском и узбекском** (переключатель EN / RU / UZ в шапке). По смыслу лаба состоит из двух частей:

1. **Целостность внутри приложения.** Сервер верит тому, что присылает сборка: хеш артефакта не пересчитывается, подпись не проверяется, профиль сборки разбирается как код, событию CI верят без подписи, а имена пакетов разрешаются сразу по двум индексам. Здесь четыре дефекта с флагами.
2. **Зависимости.** В `vulnerable/requirements.txt` намеренно закреплены старые версии с известными уязвимостями, включая транзитивные. В `fixed/` показан правильный подход: `requirements.in`, lock-файл с хешами и установка с `--require-hashes`.

## Чему научитесь

- Считать хеш от содержимого на сервере и сверять его с закреплённым значением
- Подписывать артефакты (HMAC) и проверять подпись до деплоя
- Понимать, почему данные нельзя разбирать небезопасными десериализаторами (`pickle`) и чем это заканчивается
- Проверять подпись вебхуков и отклонять неподписанные события
- Закреплять версии **и хеши** зависимостей (lock-файл) и не разрешать имена по публичному индексу
- Проверять зависимости на известные уязвимости (`pip-audit`) и получать SBOM

## Запуск

```bash
docker compose up --build
```

| Версия | Адрес |
|--------|-------|
| vulnerable (дефекты целостности + старые зависимости) | http://127.0.0.1:8021 |
| fixed (проверки на месте + обновлённые зависимости с хешами) | http://127.0.0.1:8022 |

Обе версии показывают один и тот же сайт — отличается только `app.py`. Откройте http://127.0.0.1:8021/ и пользуйтесь сайтом как обычный посетитель. Без Docker:

```bash
pip install -r vulnerable/requirements.txt
python vulnerable/app.py   # http://127.0.0.1:5000
```

Лабораторный ключ проекта, которым подписываются релизы и вебхуки, — `kestrel-lab-project-key` (он же показан на странице `/docs`). Ключ лежит в коде специально: без него нечего было бы проверять.

> ⚠️ Приложение уязвимо специально. Запускайте только локально и не публикуйте в интернет.

## Задание

### Часть 1. Целостность в самом приложении

Найдите в vulnerable-версии **четыре** ошибки целостности (в каждой спрятан флаг):

1. Опубликуйте релиз, у которого хеш не совпадает с содержимым артефакта, а подписи нет вообще. Сервер принял его? Пересчитывал ли он хеш сам?
2. Отправьте в профиль сборки не JSON, а base64-блоб сериализованного объекта. Что произошло **до** того, как сервер прочитал первое поле профиля?
3. Отправьте событие на `/webhooks/ci` без заголовка `X-Kestrel-Signature`. Что стало со сборкой и что это значит для того, кто знает адрес?
4. Установите пакет `kestrel-utils` сначала без версии, а потом с версией `1.4.2`. Из какого индекса пришёл пакет в каждом случае и сверялся ли его хеш с тем, что закреплён в lock-файле?

Проверьте каждую из четырёх ситуаций на исправленной версии (порт 8022) и сформулируйте, что именно там изменилось. Дефекты помечены в `vulnerable/app.py` комментариями `# ДЕФЕКТ N`.

### Часть 2. Зависимости

1. Установите инструмент: `pip install pip-audit`
2. Проверьте уязвимую версию: `pip-audit -r vulnerable/requirements.txt`
3. Выясните, какие пакеты уязвимы и до каких версий их нужно обновить. Какие из них вы **не** указывали в проекте напрямую?
4. Проверьте fixed-версию той же командой: `pip-audit -r fixed/requirements.txt`
5. Откройте `fixed/requirements.in` и `fixed/requirements.txt`. Чем они отличаются и зачем нужны хеши?
6. Эксперимент: скопируйте `fixed/requirements.txt`, замените любой хеш на нули и попробуйте `pip install --require-hashes -r <файл>`. Что произойдёт?

## Подсказки

1. Формы для всех запросов есть на страницах `/builds` и `/registry`, так что часть работы можно сделать в браузере. Для curl удобнее JSON: `curl -X POST http://127.0.0.1:8021/api/releases -H 'Content-Type: application/json' -d '{...}'`.
2. Подпись релиза — это HMAC-SHA256 от строки хеша, ключом проекта. Пример на Python есть на странице `/docs`.
3. Профиль сборки передаётся как base64 от того, что умеет разбирать `pickle`. Дальше всё зависит от того, что лежит внутри объекта.
4. Список «Публичное зеркало» на `/registry` показывает, какие пакеты приходят с внешнего индекса. Обратите внимание на хеши: они отличаются от внутренних.
5. `pip-audit` выводит имя пакета, версию, номер уведомления и версию, в которой проблема исправлена.
6. `requests` тянет за собой `urllib3`, `idna` и `certifi`, а `Flask` тянет `Werkzeug` и `Jinja2`.

Полное решение со спойлерами: [SOLUTION.ru.md](./SOLUTION.ru.md)

## Как защититься

- Считать хеш от содержимого на стороне сервера и сверять с закреплённым значением; подписывать релизы и проверять подпись перед выкаткой
- Никогда не разбирать входящие данные небезопасными десериализаторами (`pickle`, `marshal`, `yaml.load`): только JSON, схемы и валидация
- Требовать подпись у вебхуков и сравнивать её в constant-time; отклонять события без подписи
- Разрешать имена пакетов только по внутреннему индексу, закреплять версии **и хеши** в lock-файле, не включать внешний индекс как равноценный источник
- Регулярно проверять зависимости (`pip-audit`, Dependabot, аналоги), обновлять их и вести SBOM
